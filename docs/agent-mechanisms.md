# Agent 机制与问题对应表

日期：2026-10-21。实施分支：`dev`。此文按实际交付追加，质量收益须另经 P4 真实对照证明。

## 规划校验与真实停止原因

**解决的问题**：坏 JSON、缺 tool_calls 等输出曾被当成“可以回答”；轮数耗尽或重复无进展后，成功写作又覆盖停止原因，使运行轨迹看起来像证据充分。

**加入的机制**：校验规划对象和工具调用结构；非法输出显式拒绝并记录 invalid_planner_output，不调用 writer。规划前后检查预算；轮数耗尽记录 budget_exhausted。有证据且仍能安全完成写作时允许回答，但保留检索真实停止原因。

**保留的约束**：不增加公开 StopReason 枚举，错误细分放 refusal_reason/error 事件；未知工具与非法业务参数仍由 ToolExecutor 拒绝。已有引用闸门不放宽。

**证据**：`agent/tests/test_control_flow.py` 覆盖坏结构、耗尽后作答保留原因、超时前不启动规划；原 loop 无进展断言同步改为检查真实原因，不改变有据作答要求。

后续知识缺口、验证反馈、部分作答与消融接入完成后在本文分别记录，不预标为已完成。


## 显式缺口账本与调用反馈

**解决的问题**：规划只能看到短证据摘要，缺少来源范围、已试查询及错误；“搜索了很多次”不等于研究问题已解决。

**加入的机制**：GapLedger 保存最多 12 项 question/required_scope/completion_criterion、支持引用及尝试记录；条件建立后不可改写，删项不能消除未解缺口。请求 resolved 必须让条件作为 claim 经过现有 Citation Gate。规划输入携带 source_id、scope、历史调用/错误和预算；gap_ids→call_id→evidence_ids 形成追踪链，复用 plan/tool_result 事件并在任务结果增加 gaps 字段，公开回答状态不变。

**保留的约束**：账本不是新证据，不能将摘要补写成正文；没有语义支持或范围不足不闭合。旧仅 tool_calls 的规划格式仍可读，供旧消费者/固定对照使用，但不凭空声称具有缺口覆盖度。新提示词明确要求结构化 gaps。

**必要接线**：source_fetch 可从已登记 Evidence 获取来源身份，再走原逐跳获取防护；模型仍只能提供 source_id。获取时间记录实际时间。arXiv 的 /abs/ 页面不能按 fulltext 返回，报 fulltext_unavailable；PDF 正文提取未因此自动完成。

**证据**：test_gaps.py 覆盖缺正文定向读取、摘要不能闭合全文、工具失败反馈、删项/改条件、伪引用/语义不支持、搜索证据到真实 SourceFetchTool 的录制 HTTP 接线。


## 验证反馈与受限修复

**解决的问题**：旧 writer 只知道“验证失败”，不知道是无登记引用、摘要越权还是结论缺支持；重复同批证据重写可能反复失败。

**加入的机制**：ClaimCheck 增加 code/action，反馈包含失败 claim、引用、所需范围和原因；缺范围/语义支持时，planner 在剩余轮数内补读/补搜，然后重生成一次。规划输入提供五工具的已登记来源入口；未知来源不变成任意 URL 获取。初始检索与修复复用同一循环和去重记录。

**保留的约束**：最多两次 writer 调用，修复不重置任何预算；无登记引用仍拒绝，数字/专名/语义验证不放宽。工具结果和证据都是不可信数据；不会迁入自演进或任意代码能力。

## 从已验证结论重建正文与研究局限

**解决的问题**：只验证 claims 无法覆盖 writer 自由 answer 中未列出的事实；一条无据结论也会导致整题拒绝。

**加入的机制**：最终正文由通过验证的独立事实句和引用确定性拼接。第二次仍混有失败项时，仅保留此次或已验证的支持项，局限性独立返回；不直接发布未验证 answer。公开状态仍为 answered/refused，新增 limitations/gaps 默认空列表以保持兼容；HTTP/SSE 均保留，前端展示研究局限及缺口进度。

**证据**：test_repair.py 检查自由正文的无据数字不泄漏、混合结论安全部分作答、范围失败后 fetch+重生成；test_api_v1.py 检查真实 HTTP response_model/SSE 终态均保留局限性。此机制不能证明已覆盖用户问题全部方面，是否完整须看缺口及质量评测。

## 跨阶段预算和实际取消

**解决的问题**：先前验证阶段没有逐次检查剩余量，最后一次验证用量超限仍可能返回成功；仅阶段间查看时钟无法中断卡住的云请求。

**加入的机制**：planner/writer/semantic verifier 共用模型调用计账与剩余输出 max_tokens；Budget.guard 使用剩余总时限取消在途调用，验证/缺口闭合也受保护。工具调用上限用尽可以在剩余 token/时限内完成生成与验证；token/时限不足不得返回未验证答案。

**边界**：云端最终输入输出用量由响应结算，单次响应若超出可用 token 会如实记超限并拒答，不承诺能撤销已发生费用；金额硬上限仍未由本次引入。父任务取消继续抛 CancelledError，不转换成普通拒答。语义检查只接受明确 yes，避免把 not yes 误判为支持。

**证据**：test_repair.py 覆盖验证前耗尽、验证返回超限、在途超时与父任务取消；六目录回归 151 passed。


## 显式读取的上下文席位

**解决的问题**：evidence_read 虽返回原文，但 planner 原先仍只见 200 字摘要；正文还可能被旧检索结果的 top8 挤掉，造成“调用了读取工具却没有读到”。

**加入的机制**：仅对成功且已登记的 fetch/read 结果提供最多 4000 字摘录，供下一轮 planner 和 writer 使用；显式读取结果优先占据最多 8 条写作上下文席位，再用原 RRF 结果补齐。检索指标仍按独立 RRF 全序计算，不把阅读优先次序冒充检索排名提升。规划提示列出实际可用工具与参数。

**证据**：test_gaps.py 放置 10 条无关证据，目标事实位于第 1800 字后，验证一次真实 EvidenceReadTool 调用后 planner/writer 都能读到目标；原实现先红，修正后 agent 53 passed。

**消融开关**：verification_feedback=False 同时关闭失败反馈内容、补检索和最终部分作答分支，避免 gap-only 对照意外获得反馈机制。正文安全重建和预算修正仍是两种新流程的共同基础，不能将其收益全归因于 gap。


## 固定旧版本、消融与来源快照对照

**解决的问题**：只测修改后的代码无法知道收益来自哪里；更换模型、网页变化或额外预算也会造成虚假的架构增益。

**加入的机制**：独立 agent-improvement.freeze.json 固定旧 loop 提交与源码 hash、原冻结件 hash、页级文本指纹、三组定义与相同预算。评测专用入口读取并校验本仓库旧 loop 源码，不复制旧业务文件到生产；baseline/gaps/feedback 共用 provider/evidence/Reader 与五工具环境。gaps 组保留安全/控制修正但关闭反馈与最终部分作答，不能将所有差异都归为缺口单因素。

**来源控制**：按 tool+args 共享首次外部响应（含失败），在各任务的新 EvidenceStore 中重新登记；每组仍消耗自己的逻辑工具预算。保存查询、原始 Evidence 快照、cache_hit、真实外部请求数及逐题结果；随机但可复现地轮换组执行顺序。HTTP 客户端按每次任务关闭，避免资源累积。

**判读边界**：共享快照的延迟是受控实验延迟，并非完整冷启动线上成本；报告分别记外部真实请求/缓存次数。模型 token 用量可比，但未设计价表，currency_cost_unknown=true，不能宣称美元费用达标。baseline 固定的是旧 loop，其他依赖共用当前版本，不冒充完整历史系统复现。

**验收记录**：新对照机械测试 5 passed；18 题×三组×3 次共 162 次 fake 运行，三组各 54 次、0 error，各自 5 个安全样例通过。报告 not_a_conclusion=true、verified_gold=0。缺真实凭证/人工核验，P4 实际质量验收保持待执行；不进入 Supervisor 实施。


## 审查补齐：核验窗口、候选保留与引用证据快照

**解决的问题**：显式读取扩大到 4000 字但语义核验仍截 2000 字，会再次误拒后半段有据事实；第二次输出全失败会丢失首轮已支持结论；补搜挤出原 top8 后，部分回答的引用可能不在返回 Evidence 中。

**加入的机制**：READ_CONTEXT_CHARS 共享读/写/语义核验上界；跨两次尝试保留已通过闸门的候选，完整成功只发布本次通过项，部分回退从已验证候选重建。发布时从 EvidenceStore 补齐最终每个 citation_id 的原始证据，输出证据数可以超过写作上下文 8 条，不扩大模型调用窗口。

**证据**：两路独立审查只读复现后，新增 3 项真实 loop 回归先红后绿，repair 11 passed；覆盖第 2200 字后的支持事实、首轮部分有据/次轮全失败、补读 8 条新正文后原引用仍可解析。
