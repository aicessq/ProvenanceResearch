# 项目技术栈文档

本文档不是讲“架构怎么流动”，而是专门回答：

- 这个项目到底用了哪些技术？
- 每种技术在项目里承担什么职责？
- 面试时应该怎么解释为什么选它？

---

## 1. 技术栈总览

当前项目的核心技术栈可以分成 8 组：

1. Python 3.11+
2. FastAPI + Pydantic v2
3. SQLAlchemy + Alembic + PostgreSQL
4. Redis + Celery
5. Qdrant
6. PyMuPDF
7. sentence-transformers + torch
8. Docker / Docker Compose
9. pytest + TestClient + httpx

---

## 2. Python 3.11+

### 用在什么地方

- 整个后端主语言
- 在 `pyproject.toml` 中要求 `requires-python = ">=3.11"`

### 在本项目里的价值

- 作为整个后端的基础运行时
- 支撑类型注解、dataclass、现代异步 / 同步 Python 开发体验

### 面试可以怎么说

可以说：

> 我们选择 Python 3.11+，因为它对 FastAPI、Pydantic v2、SQLAlchemy 2.x、Celery、AI/NLP 生态都很友好，而且比较适合快速构建 RAG 后端系统。

---

## 3. FastAPI

### 用在什么地方

- `backend/app/main.py`
- `backend/app/api/*`

### 在本项目里的职责

- 提供 HTTP API
- 组织路由
- 自动生成 Swagger 文档
- 作为整个后端系统的统一入口

### 为什么适合这个项目

- API 开发效率高
- 天然适合 Pydantic 数据校验
- 文档友好，调试方便
- 很适合快速构建分阶段演进的后端

### 面试可以怎么说

> FastAPI 在这个项目里是 API 外壳，它不负责核心业务逻辑，但负责把上传、查询、文档替换、评测这些能力以统一 HTTP 接口对外暴露出来。

---

## 4. Pydantic v2

### 用在什么地方

- `backend/app/schemas/*`
- `backend/app/config.py`

### 在本项目里的职责

- 请求 / 响应 schema 定义
- 配置对象建模
- 参数校验与默认值管理

### 为什么适合这个项目

- 与 FastAPI 配合紧密
- 明确区分输入输出契约
- 能降低接口层与业务层之间的数据歧义

### 面试可以怎么说

> Pydantic 让接口契约很清晰，比如 query、answer、eval 这类接口都能通过 schema 明确约束字段结构，减少“前后端靠约定猜字段”的问题。

---

## 5. SQLAlchemy 2.x

### 用在什么地方

- `backend/app/db/`
- `backend/app/models/*`
- 多数 service 中的数据库读写逻辑

### 在本项目里的职责

- ORM 映射
- Session 管理
- 持久化 documents / versions / chunks / tasks / query_logs / eval_runs 等数据

### 为什么适合这个项目

- 关系型建模能力强
- 适合 document-version-chunk 这类结构复杂的模型
- 与 Alembic 配合成熟

### 面试可以怎么说

> 我们不是做一个只有 prompt 的 Demo，而是一个有真实文档生命周期和检索资产管理的系统，所以 ORM 和关系型建模是必要的，SQLAlchemy 适合承载这种复杂业务对象关系。

---

## 6. Alembic

### 用在什么地方

- `backend/alembic/`
- `backend/alembic.ini`

### 在本项目里的职责

- 管理数据库 schema 迁移
- 保证从开发环境到部署环境的表结构一致

### 为什么适合这个项目

- 和 SQLAlchemy 官方生态一致
- 适合多阶段演进的项目
- 能把 Phase 1 以后新增的数据结构稳定沉淀下来

### 面试可以怎么说

> 因为这个项目的数据模型是持续演进的，比如后面增加了 query_logs、eval_runs 等表，所以必须用迁移工具管理 schema，而不是手工改库。

---

## 7. PostgreSQL

### 用在什么地方

- `docker-compose.yml`
- `backend/app/models/*`
- `backend/app/services/keyword_store.py`

### 在本项目里的职责

- 主业务数据库
- 保存文档、版本、chunk、任务、日志、评测数据
- 承担 PostgreSQL FTS 关键词检索

### 为什么适合这个项目

- 关系型数据能力强
- JSONB、UUID、GIN index 等都很适合 RAG 资产管理
- 可以同时承担结构化数据和 FTS

### 面试可以怎么说

> PostgreSQL 在这个系统里不仅是主数据库，还承担了关键词检索能力，所以它既是业务库，也是 hybrid retrieval 里的 keyword 检索底座。

---

## 8. Redis

### 用在什么地方

- `docker-compose.yml`
- Celery 任务链路
- 任务状态相关逻辑

### 在本项目里的职责

- Celery broker / result backend
- 实时状态缓存
- 支撑异步任务通信

### 为什么适合这个项目

- 轻量、成熟
- 与 Celery 组合常见
- 对 ingest / replace 这种异步任务场景足够合适

### 面试可以怎么说

> Redis 在这里不是为了做复杂缓存系统，而是作为任务调度与状态协作的基础设施，用来配合 Celery 跑文档处理链路。

---

## 9. Celery

### 用在什么地方

- `backend/app/workers/*`
- `docker-compose.yml` 中的 `worker` 服务

### 在本项目里的职责

- 执行 ingest / replace / reindex 等异步任务
- 把长耗时工作从同步接口中拆出去

### 为什么适合这个项目

- 文档解析、切分、embedding、索引写入都不适合同步阻塞 API
- Celery 和 Redis 组合成熟
- 易于部署成独立 worker 进程

### 面试可以怎么说

> 在这个项目里，Celery 的主要价值是让上传接口只负责“接收请求和创建任务”，真正重的文档处理放到后台 worker，避免接口超时和用户等待过久。

---

## 10. Qdrant

### 用在什么地方

- `docker-compose.yml`
- `backend/app/services/vector_store.py`
- retrieval 相关 service

### 在本项目里的职责

- 保存 child chunk 向量
- 提供向量检索
- 支撑 hybrid retrieval 中的 semantic search 部分

### 为什么适合这个项目

- 作为向量数据库，接口直接、部署相对轻量
- 适合中小型 RAG 系统快速落地
- payload 机制适合带元数据过滤

### 面试可以怎么说

> 我们没有把所有文本都放到向量库里，而是只索引 child chunk；Qdrant 负责语义检索，而 parent chunk 只作为上下文回填资源存在数据库里。

---

## 11. PyMuPDF

### 用在什么地方

- `pyproject.toml`
- `backend/app/services/parser_service.py`

### 在本项目里的职责

- PDF 逐页解析
- 为后续清洗、chunk、页码引用提供基础文本来源

### 为什么适合这个项目

- PDF 是这个知识库的重要输入格式
- PyMuPDF 在逐页读取、速度和工程实用性上比较合适

### 面试可以怎么说

> 这个项目不是只吃纯文本，法规、标准、教材大量是 PDF，所以必须有可靠的 PDF 解析能力，PyMuPDF 就是 ingest 链路的基础技术之一。

---

## 12. sentence-transformers

### 用在什么地方

- `pyproject.toml`
- `backend/app/services/embedding_service.py`
- `backend/app/services/reranker.py`

### 在本项目里的职责

- 封装本地 embedding 模型
- 封装 reranker 模型调用

### 为什么适合这个项目

- Hugging Face / Sentence Transformers 生态成熟
- 适合快速接入本地语义模型
- 对 RAG 任务非常常见

### 面试可以怎么说

> 我们把 embedding 和 reranker 都放在服务层里做封装，底层依赖 sentence-transformers 生态，这样可以把模型替换成本地不同实现而不影响 API 层。

---

## 13. torch

### 用在什么地方

- `pyproject.toml`
- 本地 embedding / reranker 模型运行依赖

### 在本项目里的职责

- 为本地 AI 模型推理提供底层张量计算能力

### 为什么适合这个项目

- 本地 embedding / reranker 基本离不开深度学习运行时
- torch 是最常见的依赖之一

### 面试可以怎么说

> 在这个项目中，torch 不是拿来做训练的，主要是支撑本地向量模型和重排模型推理。

---

## 14. Docker / Docker Compose

### 用在什么地方

- `docker-compose.yml`
- `backend/Dockerfile`

### 在本项目里的职责

- 一键编排后端与依赖服务
- 统一开发环境 / 体验环境
- 降低基础设施启动门槛

### 为什么适合这个项目

- 这个项目依赖 PostgreSQL、Redis、Qdrant、worker，多组件协作明显
- Docker Compose 能显著降低环境准备成本

### 面试可以怎么说

> 这个项目不是单进程脚本，而是典型的多服务后端系统，所以 Docker Compose 主要解决的是“把所有依赖稳定拉起来”的问题。

---

## 15. pytest

### 用在什么地方

- `backend/tests/`
- `pyproject.toml`

### 在本项目里的职责

- 单元测试与集成测试
- 验证各阶段功能落地是否正确

### 为什么适合这个项目

- Python 主流测试框架
- 与 FastAPI / SQLAlchemy / httpx 生态兼容好
- 对分阶段迭代项目友好

### 面试可以怎么说

> 我们的测试不是只测一个 health，而是随着 phase 推进逐步覆盖 parser、chunk、retrieve、answer、update、eval 等模块，而且把 integration 测试单独标记，便于本地和基础设施环境分开执行。

---

## 16. FastAPI TestClient / httpx

### 用在什么地方

- `backend/tests/conftest.py`
- 接口层测试文件

### 在本项目里的职责

- 模拟 HTTP 请求
- 测试接口响应结构与状态码

### 为什么适合这个项目

- FastAPI 自带良好支持
- 对接口层验证简单直接

### 面试可以怎么说

> 我们在 API 层主要用 TestClient 验证请求和响应契约，而更深的业务逻辑则在 service 测试里覆盖，这样分层更清晰。

## 17. 技术栈之间的协作方式

如果把这些技术拼起来，当前项目的协作关系可以简化成：

```text
FastAPI + Pydantic
  -> 提供 API 与数据契约
SQLAlchemy + PostgreSQL
  -> 承担业务数据与 FTS
Redis + Celery
  -> 承担异步任务体系
Qdrant + embedding / reranker
  -> 承担语义检索与排序
PyMuPDF + parser/cleaner/chunk
  -> 承担知识入库前处理
pytest + TestClient
  -> 承担验证体系
Docker Compose
  -> 把整套服务编排起来
```

---

## 18. 面试时最适合强调的技术选型逻辑

你可以把项目的技术选型逻辑总结成下面几条：

1. **FastAPI + Pydantic**：提高 API 和数据契约开发效率。
2. **PostgreSQL**：不仅存业务数据，还承担 FTS，是 hybrid retrieval 的一部分。
3. **Qdrant**：专门负责向量检索，不和主数据库职责混淆。
4. **Redis + Celery**：把重处理从同步请求里拆出来。
5. **PyMuPDF**：解决 PDF 文档真实入库问题。
6. **本地 embedding / reranker**：让检索与重排能力可控。
7. **pytest + integration 标记**：让测试既能轻量运行，也能做真实基础设施验证。
8. **Docker Compose**：降低多组件系统的启动复杂度。

---

## 19. 一句话总结技术栈

如果要一句话概括当前项目技术栈，可以这样说：

> 这是一个用 FastAPI 构建 API、用 PostgreSQL 管业务数据和 FTS、用 Qdrant 做向量检索、用 Redis + Celery 跑异步任务、用本地 embedding/reranker 提升检索质量、再通过 pytest 和 Docker Compose 保证可验证与可运行的安全领域 RAG 后端系统。
