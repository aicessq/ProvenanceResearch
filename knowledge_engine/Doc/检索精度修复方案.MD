# 检索精度修复方案（审计稿）

## 1. 文档状态与执行门禁

- 状态：**待审计，禁止执行**。
- 适用问题：查询“什么是个人信息”时，系统优先返回《网络安全法》第四十条、第五十条等弱相关内容，未优先返回“个人信息，是指……”的定义条款。
- 本文只规定诊断、修复、迁移和验收方案，不代表已修改代码、配置、数据库或向量索引。
- 未经审计人明确批准，不得执行模型切换、索引重建、数据清理或代码修改。
- `Doc/文档2.MD` 仍是权威可执行规范；本文若与其冲突，以该规范为准。

## 2. 已知现象

1. 查询“什么是个人信息”时，向量结果主要为第四十条、第五十条等弱相关条款。
2. 返回结果的向量分数约为 `0.05～0.07`，没有明显高相关候选。
3. 同一法规、同一条款以不同 `document_id`、`version_id` 和 `chunk_id` 重复出现，占用多个候选名额。
4. 将定义原文作为更长查询时，结果仍可能漂移至法律责任条款。
5. 文档库中存在目标定义文本，但其召回和排序不符合预期。

## 3. 根因假设与证据等级

### P0-1：运行时使用无语义能力的 fallback embedding，或索引模型与查询模型不一致

**证据：强，尚需运行时确认。**

- fallback embedding 根据文本哈希生成稳定向量，不表达语义关系。
- 查询 API、Answer 服务和 ingest worker 均允许模型加载失败后使用 fallback。
- 当前环境配置的 embedding 路径是相对路径；应用从不同工作目录启动时，可能解析到不同位置。
- 当前调试结果的低分和随查询文本变化而大幅漂移的特征，与无语义向量高度一致。
- 系统尚未持久化 embedding 模型标识，无法保证索引和查询处于同一向量空间。

**风险：** 如果该假设成立，仅调整 TopK、RRF、关键词或提示词无法恢复语义检索质量。

### P0-2：Reranker 未接入实际查询链路

**证据：确定。**

- 当前流程在向量与关键词结果经过 RRF 后直接截取最终 TopK。
- 已有 reranker 服务未被 retriever 调用。
- 定义类查询需要区分“X 是指……”与仅包含 X 的义务、处罚条款；缺少重排会直接降低最终精度。

### P0-3：重复文档污染候选集，融合阶段未按内容去重

**证据：确定。**

- 调试结果中相同条款至少出现三次，但 chunk ID 不同。
- 上传流程允许相同文件形成不同 document。
- Qdrant 和 RRF 均以 chunk ID 识别候选，相同文本不会折叠。

### P1-1：中文关键词查询使用整句，核心术语没有独立检索

**证据：强。**

- PostgreSQL FTS 使用 `simple` 配置处理整条查询。
- ILIKE fallback 仅在 FTS 完全无结果时运行，且同样使用完整查询字符串。
- “什么是个人信息”不是目标原文“个人信息，是指……”的连续子串。
- Query Rewriter 生成的 `search_keywords` 和 `sub_queries` 没有进入 retriever。

### P1-2：RRF 不考虑原始相关度，也没有最低相关度门槛

**证据：确定。**

- RRF 只使用候选名次，不使用向量绝对分数。
- 同时进入向量榜和关键词榜的弱相关条款可能超过只进入一路的定义段。
- 当前没有向量 score threshold；低分结果仍参与融合。

### P1-3：意图识别未覆盖“什么是”句式

**证据：确定。**

- 概念意图覆盖“是什么”，没有覆盖“什么是”。
- 完整 Answer 链路可能将该查询误判为 `out_of_scope`。
- `/query/retrieve` 与 `/query/answer` 的预处理行为不同，容易造成调试结果与生产问答链路不一致。

### P2：目标定义 chunk 的解析、切分、激活状态或索引状态异常

**证据：待查。**

目标文本虽然存在于原始文档，但仍需确认：

- 是否被解析为 child chunk；
- 是否存在异常断行或 OCR 噪声；
- PostgreSQL 中是否为 active/current version；
- Qdrant 中是否存在对应 point；
- FTS 字段是否已建立；
- 是否由旧 embedding 模型生成向量。

## 4. 修复原则

1. **先建立可重复的失败信号，再修改实现。**
2. **先修向量空间正确性，再调排序参数。**
3. **索引与查询必须使用同一模型、同一版本、同一归一化方式。**
4. **生产链路不得静默降级到无语义 embedding。**
5. **只检索 child chunk，parent chunk 仍仅用于上下文重建。**
6. **API 层保持薄层，修复逻辑放在 services/workers。**
7. **不以单条查询调参；使用定义、义务、处罚、操作类查询共同验收。**
8. **所有数据清理和索引重建必须可审计、可回滚。**

## 5. 分阶段修复计划

## 阶段 A：建立失败基线，不改变生产行为

### A1. 固定最小复现用例

至少覆盖以下查询：

1. `什么是个人信息`
2. `个人信息是什么`
3. `个人信息，是指以电子或者其他方式记录的能够单独或者与其他信息结合识别自然人个人身份的各种信息`
4. 一条义务类问题，例如个人信息处理者应履行什么义务
5. 一条处罚类问题，例如非法提供个人信息承担什么责任

### A2. 记录诊断字段

每条查询记录：

- 实际调用接口：`/query/retrieve` 或 `/query/answer`；
- 原始查询、改写查询、意图、扩展术语和 metadata filters；
- embedding 实现类、模型路径、模型标识和向量维度；
- vector top 30、keyword top 30、fused top 20；
- 每个候选的 vector rank、keyword rank、原始分数和 RRF 分数；
- 最终证据及引用。

日志不得记录密钥、完整环境变量或不必要的用户敏感内容。

### A3. 建立红灯测试

新增或扩展测试，确保修复前能够稳定捕获：

- “个人信息”定义段未进入最终 TopK；
- 相同文本、不同 chunk ID 重复占位；
- “什么是”被误判；
- RRF 双路弱相关候选压过单路高相关候选；
- fallback 模型被生产查询或 worker 静默使用。

**阶段 A 通过条件：** 存在一条可重复执行的测试或脚本，能够稳定复现用户报告的错误排序，并保存修复前基线。

## 阶段 B：修复模型加载和向量空间一致性

### B1. 明确运行时模型路径

- 统一 backend 与 worker 的工作目录和模型路径解析规则。
- 优先使用明确的容器内绝对路径或由 Settings 解析后的规范路径。
- 启动时校验模型目录、配置和权重是否存在。
- readiness 应暴露“真实模型是否就绪”，但不得泄露本机绝对路径或环境秘密。

### B2. 禁止生产环境静默 fallback

建议区分环境策略：

- 测试环境：可显式允许 deterministic fallback，用于编排测试；
- 开发/生产检索和 ingest：真实模型加载失败时快速失败，并给出结构化错误；
- 禁止 worker 使用 fallback 建索引而 backend 使用真实模型查询，反之亦然。

### B3. 建立模型身份

定义可持久化的 embedding 身份，至少包含：

- 模型名称或本地版本；
- 模型目录内容版本或权重摘要；
- 向量维度；
- 归一化配置；
- 文本预处理版本。

Qdrant collection 或独立元数据中应保存该身份。查询启动时若身份不一致，应拒绝服务并要求重建索引，而不是继续检索。

### B4. 全量重建向量索引

只要确认历史索引使用了 fallback 或不同模型，就必须：

1. 备份或记录当前 collection 状态；
2. 使用新的临时 collection 名称构建索引；
3. 只写入 active、current-version child chunks；
4. 验证数量、payload、模型身份和抽样检索结果；
5. 验收通过后切换 collection；
6. 保留旧 collection 至观察结束，再按批准流程删除。

不得在未知模型空间的旧 collection 上直接混写新向量。

**阶段 B 通过条件：** backend 与 worker 均加载相同真实模型；定义类基准查询的 vector top 30 能稳定召回目标定义 chunk；不存在模型身份不一致。

## 阶段 C：修复候选去重和重复文档治理

### C1. 查询时内容去重

在融合后、reranker 前按内容身份折叠重复候选。建议优先级：

1. `chunk_hash`；
2. 若历史数据缺少可靠 hash，则使用规范化文本摘要；
3. 保留一个代表候选，并记录重复来源列表供引用或调试。

不能只按 chunk ID 去重。

### C2. 防止新增重复文档

上传时检测全库相同 `file_hash`：

- 默认拒绝重复上传，并返回已有文档标识；或
- 若业务允许副本，要求用户显式确认，同时检索层仍应按内容折叠。

该决策需要审计人选择，不能在实施时自行决定。

### C3. 治理历史重复数据

先生成只读报告，再决定处理方式：

- 按 `file_hash` 统计重复 document；
- 按 `chunk_hash` 统计 active 重复 chunk；
- 标出当前版本、引用关系和 ingest task；
- 默认不物理删除；优先软删除明确的重复 document，并同步 PostgreSQL、FTS 和 Qdrant 可见性。

**阶段 C 通过条件：** 同一规范化条款在最终候选中只占一个位置；重复来源不再挤占 TopK；历史处理有审计清单和回滚记录。

## 阶段 D：修复中文查询准备和关键词召回

### D1. 修复意图识别

概念类至少覆盖：

- `什么是X`
- `X是什么`
- `X的定义`
- `如何定义X`
- `X是指什么`

同时收紧法规意图规则，避免因查询中任意出现“法”或“条”单字而误分类。

### D2. 补齐术语扩展

按照权威规范加入“个人信息”等术语映射。术语扩展应作为召回辅助，不得把所有同义词简单拼接成长向量查询。

### D3. 消费 `search_keywords` 和 `sub_queries`

建议检索策略：

- rewritten query：用于主向量检索；
- 核心实体/术语：用于关键词检索；
- 必要的 sub-query：分别召回后融合；
- 对定义意图可加入轻量结构信号，如“是指、定义”，但不能硬编码某一法规答案。

### D4. 改善中文关键词路径

最低可行修复：

- 不再仅使用整句进行 ILIKE；
- 独立使用规范化核心关键词，例如“个人信息”；
- 即使 FTS 返回其他候选，也允许关键词 fallback 补充候选，而不是只在零结果时运行。

若引入中文分词或新的 PostgreSQL 扩展，必须单独审计部署复杂度；本轮优先采用现有基础设施内的最小修复。

**阶段 D 通过条件：** 目标定义 chunk 能通过关键词路径召回；“什么是个人信息”和“个人信息是什么”的准备结果一致且属于概念查询。

## 阶段 E：接入真实 Reranker

### E1. 接入位置

严格按照规范：

```text
vector top 30 + keyword top 30
→ 内容去重
→ RRF
→ fused top 20
→ reranker
→ evidence top 5
→ parent context reconstruction
```

### E2. 模型策略

- 生产环境必须加载真实 reranker；加载失败策略需显式配置。
- 不允许使用固定分数或无语义实现冒充质量验证。
- 记录 reranker 模型身份和耗时，不记录模型敏感配置。

### E3. 结果字段

query log 应保存：

- fused chunk IDs；
- reranked chunk IDs；
- 最终 evidence IDs；
- 必要的分数和延迟。

**阶段 E 通过条件：** 定义段在候选已召回时可被稳定提升至最终证据前列；reranked IDs 不再为空。

## 阶段 F：校准融合和拒答策略

仅在 B～E 完成后进行，避免用参数掩盖基础链路错误。

### F1. 评估 RRF

评估以下方案，但不预设一定替换 RRF：

- 保留标准 RRF；
- 向量和关键词分路加权；
- 使用归一化原始分数作为辅助；
- 对重复来源不重复加分。

选择必须由离线评估指标驱动。

### F2. 相关度门槛

不得直接把当前 `0.05～0.07` 设为阈值依据。先在真实模型和一致索引上统计正负样本分布，再确定：

- 最低向量相关度；
- 最低 reranker 分数；
- 无充分证据时的拒答规则。

**阶段 F 通过条件：** 阈值来自评估集，不是针对单条问题手工拟合；低证据查询能够稳定拒答而不是返回随机条款。

## 7. 测试计划

### 7.1 快速测试

至少新增或更新：

1. fallback 仅在显式测试配置下可用；
2. 模型身份不一致时拒绝查询或索引；
3. “什么是”和“是什么”均识别为概念查询；
4. “个人信息”术语扩展正确；
5. `search_keywords` 确实进入关键词检索；
6. 相同文本、不同 chunk ID 被折叠；
7. RRF 后调用 reranker，并记录 reranked IDs；
8. parent chunk 不进入直接检索。

### 7.2 集成测试

在 PostgreSQL、Redis 和 Qdrant 可用时验证：

1. 真实 child chunk 入库并建立 FTS/Qdrant 索引；
2. 定义文本可被向量和关键词至少一路召回；
3. 重复 document 不会产生重复最终候选；
4. replace 和 soft delete 后三类可见性保持一致；
5. 新 collection 切换后无旧模型向量混入。

集成测试必须使用独立测试数据库和 collection。

### 7.3 评估集

扩充 `eval/golden_dataset.jsonl`，至少包含：

- 定义类；
- 法规义务类；
- 法律责任类；
- 跨条款比较类；
- 无答案/应拒答类；
- 同义表达和查询词序变化；
- 重复文档场景。

主要指标：

- Recall@5、Recall@20；
- MRR；
- 最终证据准确率；
- 引用准确率；
- 重复结果率；
- 拒答准确率；
- P50/P95 检索与重排延迟。

## 8. 验收标准

修复不能仅以“该查询能回答”为标准。至少满足：

1. “什么是个人信息”的目标定义 chunk 稳定进入 vector/keyword 候选，并位于最终证据前 3。
2. “个人信息是什么”等等价表达得到相同核心证据。
3. 同一条款的重复副本在最终候选中只出现一次。
4. backend 和 worker 报告相同 embedding 模型身份。
5. 生产模式下真实模型缺失会明确失败，不会静默生成无语义索引。
6. reranker 实际执行，query log 中存在 reranked chunk IDs。
7. Recall@5、MRR、引用准确率不得低于修复前基线；具体提升门槛由审计人在执行前填写。
8. 默认快速测试全部通过；真实基础设施集成测试全部通过。
9. replace、soft delete、eval 流程无回归。

## 9. 回滚方案

1. 代码修改按阶段提交，禁止把模型加载、数据清理、关键词改造和 reranker 接入混成一个不可拆分变更。
2. 新向量使用临时 collection 构建，验收后再切换配置。
3. 切换前保留旧 collection 和对应模型身份记录。
4. 历史重复文档优先软删除，不进行不可逆物理清理。
5. 若新链路指标退化，回切旧 collection 和上一版本代码；不得把新旧模型向量混合写入同一 collection。

## 10. 审计决策项

执行前请明确批准或修改以下决策：

- [ ] 是否批准生产/开发检索禁止静默 embedding fallback。
- [ ] 是否批准为模型身份增加持久化校验。
- [ ] 是否批准使用新 Qdrant collection 全量重建索引。
- [ ] 上传相同 `file_hash` 时选择：拒绝 / 显式确认后保留副本。
- [ ] 历史重复文档选择：仅查询时折叠 / 审计后软删除副本。
- [ ] 是否批准 `chunk_hash` 作为查询结果主要内容去重键。
- [ ] 是否批准按规范接入真实 reranker。
- [ ] 是否批准扩充评估集并以指标作为上线门禁。
- [ ] 填写 Recall@5、MRR、引用准确率和延迟的最低验收门槛。

## 11. 建议执行顺序

审计通过后严格按以下顺序实施：

1. 阶段 A：建立失败测试和修复前基线；
2. 阶段 B：确认真实模型、模型身份并重建一致索引；
3. 阶段 C：查询去重和重复文档治理；
4. 阶段 D：中文意图、核心关键词和多查询召回；
5. 阶段 E：接入真实 reranker；
6. 阶段 F：根据评估集校准融合与拒答阈值；
7. 执行完整快速测试、集成测试和 eval；
8. 提交验收结果，等待上线批准。

任何阶段未达到通过条件，应停止后续实施并回到该阶段调查，不得通过提高 TopK 或硬编码目标答案绕过问题。
