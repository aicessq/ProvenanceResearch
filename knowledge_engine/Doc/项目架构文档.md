# 项目架构文档

本文档描述的是**当前仓库已经实现出来的真实架构**，不是最初规划中的理想图。阅读目标是帮助你从代码层面理解：这个项目由哪些模块组成、请求如何流动、数据如何落库、异步任务如何协作。

---

## 1. 项目整体定位

这是一个面向**网络安全领域知识资料**的 RAG 后端项目，主要服务对象包括：

- 网络安全法律法规
- 安全标准
- 教材 / 手册 / 笔记
- 与网络安全相关的知识型资料

它的目标不是做一个泛化聊天机器人，而是做一个：

- 能上传与版本化文档
- 能解析、清洗、切分并建立索引
- 能基于混合检索给出带引用的回答
- 能做增量更新与软删除
- 能运行评测并量化系统效果

## 3. 运行时分层

当前代码遵循比较清晰的分层：

### 3.1 入口层：FastAPI 应用

入口文件是：

- `backend/app/main.py`

它负责：

- 创建 FastAPI 应用
- 初始化日志
- 挂载 `/api/v1` 路由
- 提供根路径 `/health`
- 提供全局异常兜底

这一层尽量保持“薄”，不承载业务逻辑。

### 3.2 路由层：API 聚合与接口模块

路由聚合在：

- `backend/app/api/__init__.py`

当前已接入的接口域包括：

- `health`
- `upload`
- `documents`
- `query`
- `eval`

每个路由文件只负责：

- 定义 HTTP 路径
- 解析请求参数
- 调用 service
- 做基础错误映射

### 3.3 业务层：services

`backend/app/services/` 是系统最关键的一层。它承载：

- 文档解析
- 清洗
- chunk 切分
- embedding 封装
- 向量存储封装
- 关键词检索封装
- safety guard
- intent / rewrite
- answer generation
- citation checking
- update / replace / soft delete
- eval run

也就是说，这个项目的主要工程思想是：

> **API 层只接请求，真正的业务逻辑都沉到 services 层。**

### 3.4 持久化层：db + models + Alembic

数据库相关逻辑由以下部分组成：

- `backend/app/db/base.py`
- `backend/app/db/session.py`
- `backend/app/models/*.py`
- `backend/alembic/`

`db/session.py` 负责 engine / SessionLocal，`models/` 负责 ORM 模型定义，Alembic 负责 schema 迁移。

### 3.5 异步处理层：workers

异步任务位于：

- `backend/app/workers/`

当前 worker 体系主要基于 Celery，用于处理：

- ingest
- replace / reindex 类任务

这保证了上传、替换、索引类工作不必阻塞同步 HTTP 请求。

## 4. 领域模型架构

当前系统的重要数据实体主要包括：

- `documents`
- `document_versions`
- `chunks`
- `ingest_tasks`
- `query_logs`
- `feedback`
- `eval_datasets`
- `eval_dataset_items`
- `eval_runs`
- `eval_run_items`

### 4.1 documents / document_versions

这是文档与版本的核心关系：

- `documents`：逻辑上的文档主体
- `document_versions`：某个文档的具体版本

这样设计的目的，是让“上传新文档”和“替换已有文档版本”严格区分。

### 4.2 chunks

`chunks` 表是 RAG 的核心中间层，当前系统已经实现：

- parent / child chunk
- `chunk_hash`
- `normalized_text`
- 页码、章节、条款号等结构化元数据
- `search_tsv`
- `is_active`
- `parent_chunk_id`

这个设计支撑了后续：

- child-only 索引
- parent-context 回填
- 增量更新 diff
- 软删除可见性控制

### 4.3 ingest_tasks

`ingest_tasks` 用于记录异步任务状态，包括：

- ingest
- replace
- reindex

这部分和 Redis / Celery 共同构成任务处理体系。

### 4.4 eval 相关表

Phase 10 新增的评测体系使用：

- `eval_datasets`
- `eval_dataset_items`
- `eval_runs`
- `eval_run_items`

这让评测不只是一次性命令，而是可持久化、可比较的数据资产。

## 5. 基础设施架构

当前 `docker-compose.yml` 会编排以下服务：

### 5.1 PostgreSQL

职责：

- 保存文档、版本、chunk、任务、query log、eval run 等结构化数据

### 5.2 Redis

职责：

- Celery broker / result backend
- 任务状态缓存

### 5.3 Qdrant

职责：

- child chunk 向量检索
- 支撑 hybrid retrieval 的 vector 部分

### 5.4 Backend

职责：

- 提供 FastAPI API
- 对外暴露 `/health`、`/docs` 与 `/api/v1/*`

### 5.5 Worker

职责：

- 跑 Celery worker
- 执行 ingest / replace / reindex 等异步链路

## 6. Ingest 架构

当前 ingest 体系的主链路可以这样理解：

```text
upload request
  -> 保存原始文件
  -> 计算 file_hash
  -> 创建 document / document_version / ingest_task
  -> 进入 Celery worker
  -> parser_service
  -> cleaner_service
  -> chunk_service
  -> chunks 落库
  -> embedding / index 写入
  -> 任务完成
```

### 6.1 同步部分

HTTP 上传接口负责做轻量工作：

- 接收文件
- 创建必要数据库记录
- 把真正耗时任务交给异步层

### 6.2 异步部分

worker 负责真正的处理主流程：

- 解析 PDF / Markdown / TXT
- 清洗文本
- 切成 parent / child chunk
- 生成 hash
- 写 PostgreSQL
- 后续写向量检索与 FTS

### 6.3 为什么要异步化

因为：

- 文件解析耗时
- chunk 与 embedding 较重
- 检索索引写入不是瞬时操作

如果都放在同步请求里，会直接拉高接口延迟并降低稳定性。

## 7. Query 架构

Query 主链路当前已经实现到回答层，整体是：

```text
user query
  -> safety_guard
  -> intent_classifier
  -> term_expander
  -> query_rewriter
  -> metadata_filter_builder
  -> vector search (Qdrant)
  -> keyword search (PostgreSQL FTS)
  -> RRF fusion
  -> reranker
  -> parent-context fetch
  -> answer_generator
  -> citation_checker
  -> answer response + query_log
```

### 7.1 safety_guard 是第一道门

安全边界被放在 query 链路最前面，优先决定：

- allow
- refuse
- redirect

这对安全领域项目非常关键，因为它不是普通问答系统。

### 7.2 retrieval 是混合检索

当前实现不是只做向量检索，而是把两条路径结合：

- 向量检索：Qdrant
- 关键词检索：PostgreSQL FTS

然后再通过 RRF 做融合。

### 7.3 回答不是直接拼接检索结果

检索得到 child chunk 后，会继续：

- 回取 parent context
- 调用 answer generator 生成回答
- 用 citation checker 做最低限度证据一致性校验

所以当前系统已经具备了“带证据约束的回答”能力。

---

## 8. Replace / Update / Delete 架构

Phase 9 以后，项目不再只是“能上传”，而是有了持续维护能力。

### 8.1 replace

主语义：

- `upload`：创建新 document
- `replace`：为已有 document 创建新 version

### 8.2 增量更新

更新链路当前已经实现：

- `file_hash` 快速判断文件是否完全未变
- `chunk_hash diff`
- added / removed / unchanged child 区分
- unchanged child 向量复用

### 8.3 soft delete

删除不是简单删主表，而是同步关闭：

- document 可见性
- chunk 可见性
- Qdrant payload `is_active`
- FTS 可见性

这样才能保证默认检索范围不会再看到已删除内容。

## 9. Eval 架构

Phase 10 引入了评测体系，整体链路是：

```text
golden_dataset.jsonl
  -> load dataset
  -> bootstrap eval_dataset / eval_dataset_items
  -> create eval_run
  -> per item execute query pipeline core
  -> compute Recall@K / MRR / citation accuracy / refusal accuracy
  -> persist eval_run_items
  -> aggregate run summary
```

### 9.1 数据集位置

当前默认数据集在：

- `eval/golden_dataset.jsonl`

### 9.2 评测服务

核心服务是：

- `backend/app/services/eval_service.py`

### 9.3 评测接口

HTTP 入口是：

- `POST /api/v1/eval/run`

### 9.4 架构意义

这说明项目已经不仅能运行，还开始具备：

- 可重复评测
- 指标化比较
- 版本演进后的效果回归验证

- `backend/tests/`

当前测试是分层组织的：

- 轻量接口与配置测试
- 集成测试（依赖真实基础设施）

## 12. 当前架构的核心设计原则

可以把当前项目的架构原则总结为 6 点：

1. **入口薄，业务厚**：API 层只接请求，核心逻辑在 service。
2. **同步轻，异步重**：上传 / 替换只做轻量入口，重处理交给 worker。
3. **结构化文档建模**：document、version、chunk 分层明确。
4. **child-only 检索，parent-only 补上下文**：提高检索效率并保留可解释性。
5. **安全边界前置**：safety_guard 放在 query 链路最前面。
6. **可维护 + 可评测**：Phase 9 解决更新维护，Phase 10 解决量化验证。

## 13. 运行一致性与关键状态机

### 13.1 Ingest 状态

```text
queued → processing → parse/clean/chunk → child index + FTS → completed(100)
                                      ↘ failed（持久化错误原因）
```

PostgreSQL 是任务审计与业务读取的事实源；Redis 同时承担 Celery broker/result backend。`completed` 必须表示 chunk、child vector 和 FTS 均已完成，不能仅表示文件解析结束。

### 13.2 Replace 状态

```text
候选 version → parse/rechunk → child chunk_hash diff
→ 复用 unchanged vectors → 索引 added → 隐藏 removed
→ 全部成功后切换 current_version_id
```

默认检索同时约束 active document、active/current version 和 active chunk。旧版本可保留审计，但不得混入默认结果。软删除也必须同步关闭 PostgreSQL、FTS 与 Qdrant 可见性。

### 13.3 容器边界

backend 和 worker 是不同容器，不能依赖各自容器层中的临时文件。二者把同一 `shared_storage` volume 挂到 `/app/storage`；模型目录从宿主机只读挂到 `/app/models`。backend/worker 启动前运行 Alembic，避免新数据库健康但业务表缺失。

### 13.4 失败与恢复边界

- API 验证失败返回统一顶层 `error` envelope；未捕获异常不泄漏堆栈。
- worker 捕获处理/索引异常并把任务置为 failed；重试必须以稳定 document/version/task ID 为边界。
- Qdrant、Redis、PostgreSQL 任一不可达时严格 integration 验收失败，不能 skip。
- 本地模型权重与远程 LLM 凭据属于部署前置条件；deterministic fallback 只用于测试编排，不能作为模型质量验收。

## 14. 测试与验证分层

| 层次 | 验证内容 | 不能证明什么 |
|---|---|---|
| 快速 pytest | 规则、切分、fusion、service contract | 真实基础设施与 broker 消费 |
| integration | 真实 PG/Redis/Qdrant、迁移、API/ORM | 独立进程消息传递 |
| broker E2E | HTTP→Redis→Celery→PG/Qdrant→query | 真实模型/外部 LLM 质量（若使用 fallback） |
| 前端 build | TypeScript contract、Vite 打包 | 浏览器交互与视觉行为 |
| eval | 同一生产 query pipeline 的指标持久化 | 未提供权重/凭据时的线上质量 |

默认 `pytest` 排除 integration；严格验收必须显式运行 `pytest -m integration` 并确认 0 skip。Windows 环境若配置了 HTTP 代理，需要设置 `NO_PROXY=localhost,127.0.0.1`，否则本地 Qdrant/API 请求可能被代理为 502。

## 15. 一句话总结这个架构

如果你要非常简洁地描述当前项目架构，可以这样说：

> 这是一个基于 FastAPI 的安全领域 RAG 后端，采用“API 路由层 + service 业务层 + PostgreSQL/Redis/Qdrant/Celery 基础设施层”的分层设计，向前打通了上传、解析、切分、索引、混合检索和证据约束回答，向后补齐了增量更新、软删除与评测体系。
