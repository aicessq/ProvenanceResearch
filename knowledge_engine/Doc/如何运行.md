# 如何运行当前项目

## 1. 推荐运行方式

当前项目推荐采用以下组合：

- PostgreSQL、Redis、Qdrant：Docker Compose
- FastAPI backend：Docker Compose
- Celery worker：Docker Compose
- Celery beat：Docker Compose
- React + TypeScript + Vite 前端：宿主机 npm

backend、worker 和 beat 必须统一运行在 Docker Compose 中。backend 与 worker 共享 `/app/storage`，用于保证上传后的原始文档可以被异步任务读取。

不要使用以下混合方式：

```text
Windows 宿主机 backend + Docker worker
Docker backend + Windows 宿主机 worker
backend 与 worker 使用不同 STORAGE_ROOT
```

否则可能出现任务长期停留在 `queued`，或者 worker 消费任务后因找不到文件而转为 `failed`。

项目根目录：

```text
D:\Code_MyProject\RAG_Sec
```

## 2. 启动前准备

### 2.1 必需软件

确认已安装：

- Docker Desktop
- Node.js 与 npm
- Conda（运行后端测试时需要）

验证：

```powershell
docker version
docker compose version
node --version
npm --version
conda --version
```

### 2.2 准备环境变量

进入项目根目录：

```powershell
cd D:\Code_MyProject\RAG_Sec
```

首次运行时创建 `.env`：

```powershell
Copy-Item .env.example .env
```

Docker Compose 会自动读取根目录 `.env`。

至少检查以下配置：

```env
POSTGRES_USER=cybersec
POSTGRES_PASSWORD=cybersec
POSTGRES_DB=cybersec_rag
REDIS_DB=0
QDRANT_COLLECTION=cybersec_chunks
BACKEND_PORT=8000
```

如果需要真实 LLM 回答，再配置：

```env
LLM_API_KEY=
LLM_BASE_URL=
```

不要把真实密钥提交到仓库。

### 2.3 检查本地模型

Compose 会把根目录 `models/` 只读挂载到容器：

```text
models/embedding
models/reranker
```

模型目录为空时，项目可能使用确定性 fallback 验证流程，但这不代表真实模型检索质量。

## 3. 一键启动后端完整链路

在项目根目录执行：

```powershell
docker compose up -d --build postgres redis qdrant backend worker beat
```

该命令会启动：

| 服务 | 容器名 | 职责 |
|---|---|---|
| PostgreSQL | `cybersec-postgres` | 文档、版本、chunk、任务、日志、评测数据 |
| Redis | `cybersec-redis` | Celery broker/result backend |
| Qdrant | `cybersec-qdrant` | child chunk 向量索引 |
| Backend | `cybersec-backend` | FastAPI，并在启动时执行 `alembic upgrade head` |
| Worker | `cybersec-worker` | 解析、清洗、切分、入库和索引 |
| Beat | `cybersec-beat` | 扫描和恢复卡住的异步任务 |

首次构建需要访问 Docker Hub 拉取 `python:3.11-slim`。构建完成后检查：

```powershell
docker compose ps
```

预期：

- postgres、redis、qdrant 为 `healthy`；
- backend、worker、beat 为 `Up`。

## 4. Docker Hub 或代理问题

如果构建报错：

```text
failed to fetch anonymous token
https://auth.docker.io/token
```

说明 Docker Desktop/BuildKit 无法访问 Docker Hub，不是项目代码错误。

先测试基础镜像：

```powershell
docker pull python:3.11-slim
```

拉取成功后重新执行：

```powershell
docker compose up -d --build postgres redis qdrant backend worker beat
```

如果宿主机使用 VPN 或代理，应在 Docker Desktop 的代理设置中确认代理已生效。终端设置 `HTTP_PROXY` 并不一定能影响 Docker Desktop/BuildKit。

本地已有最新镜像时，可以临时跳过构建：

```powershell
docker compose up -d --no-build postgres redis qdrant backend worker beat
```

注意：`--no-build` 只适用于现有镜像已经包含当前代码的情况。代码修改后仍应重新构建，否则新容器可能运行旧代码。

## 5. 启动前端

后端完整链路正常后，在新终端执行：

```powershell
cd D:\Code_MyProject\RAG_Sec\frontend
npm install
npm run dev
```

前端地址：

```text
http://localhost:5173
```

Vite 会将 `/api` 请求代理到：

```text
http://localhost:8000
```

如需覆盖前端请求目标，可复制前端环境示例：

```powershell
Copy-Item .env.example .env
```

默认后端地址为：

```env
VITE_API_BASE_URL=http://localhost:8000
```

## 6. 启动后的验证

### 6.1 查看容器状态

```powershell
docker compose ps
```

### 6.2 存活检查

打开或执行：

```powershell
Invoke-RestMethod http://localhost:8000/health
```

预期：

```json
{"status":"ok"}
```

该接口只检查 FastAPI 进程存活，不检查外部依赖。

### 6.3 完整就绪检查

```powershell
Invoke-RestMethod http://localhost:8000/api/v1/health/ready | ConvertTo-Json -Depth 6
```

预期包含：

```json
{
  "status": "ok",
  "components": {
    "postgres": {"connected": true},
    "redis": {"connected": true},
    "qdrant": {"connected": true},
    "celery_worker": {
      "connected": true,
      "worker_count": 1,
      "required_tasks_registered": true
    }
  }
}
```

如果 Redis 正常但 `celery_worker.connected=false`，说明 worker 未上线、未响应检查，或关键任务没有注册。

### 6.4 验证 Worker

```powershell
docker exec cybersec-worker celery -A app.workers.celery_app.celery_app inspect ping --timeout 3
```

预期：

```text
1 node online
pong
```

检查任务注册：

```powershell
docker exec cybersec-worker celery -A app.workers.celery_app.celery_app inspect registered --timeout 3
```

应包含：

```text
app.workers.ingest_worker.ingest_document_task
app.workers.ingest_worker.replace_document_task
app.workers.recovery_worker.recover_stale_tasks
```

### 6.5 查看日志

```powershell
docker compose logs --tail 100 backend
docker compose logs --tail 100 worker
docker compose logs --tail 100 beat
```

持续跟踪：

```powershell
docker compose logs -f backend worker beat
```

### 6.6 访问地址

| 服务 | 地址 |
|---|---|
| 前端 | http://localhost:5173 |
| 后端 API | http://localhost:8000 |
| Swagger | http://localhost:8000/docs |
| 存活检查 | http://localhost:8000/health |
| 就绪检查 | http://localhost:8000/api/v1/health/ready |
| Qdrant Dashboard | http://localhost:6333/dashboard |

## 7. 上传文档与检查异步任务

通过前端上传文档后，响应会包含 `task_id`。查询任务：

```powershell
Invoke-RestMethod http://localhost:8000/api/v1/documents/tasks/<task_id> | ConvertTo-Json -Depth 6
```

正常状态流转：

```text
queued -> processing -> completed
```

任务响应包含：

- `status`
- `dispatch_status`
- `progress`
- `attempt_count`
- `recovery_count`
- `error_message`
- `last_heartbeat_at`
- `finished_at`

若任务失败，优先查看：

```powershell
docker compose logs --tail 200 worker
docker compose logs --tail 200 beat
```

## 8. 数据库迁移

backend、worker 和 beat 启动前都会执行：

```text
alembic upgrade head
```

一般不需要在宿主机重复执行迁移。

查看当前迁移版本：

```powershell
docker exec cybersec-backend alembic current
```

当前应到达：

```text
0002_ingest_task_reliability (head)
```

如需手动升级：

```powershell
docker exec cybersec-backend alembic upgrade head
```

## 9. 运行测试

Python 工作必须使用项目 Conda 环境，不要使用全局 Python。

首次准备测试环境：

```powershell
cd D:\Code_MyProject\RAG_Sec
conda create -n rag_sec_phase1 python=3.11 -y
conda run -n rag_sec_phase1 pip install -e ".[test]"
```

运行默认快速测试：

```powershell
conda run -n rag_sec_phase1 pytest
```

默认测试排除需要真实基础设施的 integration 测试。

运行集成测试前，确保完整 Compose 服务已经启动，并使用可丢弃测试数据库：

```powershell

```

注意：集成测试可能执行迁移和清理业务表，不要直接对重要数据环境运行。

前端没有独立 test 或 lint 脚本。验证前端使用：

```powershell

npm run build
```

## 10. 停止与清理

停止全部 Compose 服务：

```powershell
docker compose down
```

停止后保留 PostgreSQL、Redis、Qdrant 和共享存储命名卷中的数据。

如果要同时删除所有命名卷：

```powershell
docker compose down -v
```

警告：`-v` 会删除数据库、向量索引、Redis 数据和上传文件。除非明确要重置全部数据，否则不要执行。

## 11. 常见问题

### 11.1 上传后任务一直 queued

检查：

```powershell
docker compose ps worker beat
docker compose logs --tail 200 worker
Invoke-RestMethod http://localhost:8000/api/v1/health/ready | ConvertTo-Json -Depth 6
```

重点确认：

- worker 为 `Up`；
- `celery_worker.connected=true`；
- `required_tasks_registered=true`；
- backend、worker、beat 使用同一个 Redis；
- backend 与 worker 共享 `/app/storage`。

Beat 会周期扫描 stale queued 任务并在满足条件时重派。

### 11.2 任务从 queued 变为 failed，提示文件不存在

通常是 backend 与 worker 使用了不同文件系统，或者采用了宿主机/容器混合运行方式。

统一执行：

```powershell
docker compose up -d --build postgres redis qdrant backend worker beat
```

然后重新上传文档。

### 11.3 Readiness 显示 degraded

根据 `components` 定位：

- `postgres=false`：检查 PostgreSQL 容器和账号配置；
- `redis=false`：检查 Redis 容器和连接配置；
- `qdrant=false`：检查 Qdrant 容器；
- `celery_worker=false`：检查 worker、Redis broker 和任务注册。

### 11.4 前端显示 Failed to fetch

依次检查：

```powershell
docker compose ps
Invoke-RestMethod http://localhost:8000/health
Invoke-RestMethod http://localhost:8000/api/v1/health/ready
```

然后确认前端运行在 `http://localhost:5173`，并检查浏览器 Network 和 Console。

### 11.5 端口被占用

默认端口：

- backend：8000
- frontend：5173
- PostgreSQL：5432
- Redis：6379
- Qdrant：6333

后端端口可在根目录 `.env` 修改：

```env
BACKEND_PORT=8001
```

修改后前端的 `VITE_API_BASE_URL` 或 Vite 代理目标也需要同步调整。
