# 项目功能性问题审计结果

审计日期：2026-07-03

审计范围：当前工作区未提交改动（working tree diff），按 `/code-review` max effort 流程从功能正确性、跨文件调用、Python/FastAPI/SQLAlchemy/Celery 常见陷阱、wrapper/proxy、复用/简化/效率/分层约定等角度审计。

> 严重程度排序：越靠前越建议优先修复。

## 1. Replace 任务被投递到普通 ingest worker，而不是增量更新流程

- 文件：`backend/app/services/update_service.py:337`
- 问题：`dispatch_update_task` 实际调用 `ingest_document_task.delay(...)`。
- 影响场景：调用 `/api/v1/documents/{id}/replace` 后，`process_replace` 创建新 `DocumentVersion` 和 `task_type="replace"` 的 `IngestTask`，但普通 ingest worker 只做解析/切分/全量索引，不会调用 `apply_incremental_update`，不会切换 `document.current_version_id`、不会 amend 旧版本、不会停用被删除 chunk。
- 后果：replace 任务看似完成，但检索仍可能使用旧版本或残留旧 chunk。

## 2. ingest worker 在索引成功前提交 chunk，索引失败会留下部分入库数据

- 文件：`backend/app/workers/ingest_worker.py:95`
- 问题：chunk 持久化后立即 `db.commit()`，随后才调用 `IndexService.build_chunk_indexes(...)`。
- 影响场景：如果 commit 后 embedding、Qdrant 或 FTS 失败，`except` 中的 rollback 只能回滚后续事务，已提交的 `Chunk` 行仍留在 PostgreSQL 中，而 task 被标记为 failed。
- 后果：失败任务留下可见/半可见数据，重试可能重复 chunk，数据库侧流程可能看到失败入库内容。

## 3. Qdrant payload 未写入 chunk 正文，vector retrieval 会返回空证据文本

- 文件：`backend/app/services/index_service.py:103`
- 相关读取点：`backend/app/services/vector_store.py:171`
- 问题：`IndexService.build_payload` 保存 ID 和元数据，但不保存 `chunk.text` / `chunk_text`；`QdrantVectorStore.search` 却从 `payload.get("chunk_text") or payload.get("text")` 构造 `RetrievalHit.chunk_text`。
- 影响场景：纯向量命中的结果正文为空。
- 后果：`/query/answer` 拿到空证据上下文，答案生成与引用校验都可能失效或质量显著下降。

## 4. 向量检索没有落实默认 current_version_only 约束

- 文件：`backend/app/services/vector_store.py:203`
- 问题：`MetadataFilter.current_version_only` 默认 `True`，但 `_build_qdrant_filter` 只下推 `chunk_type`、`is_active`、`version_status` 等 payload 字段，无法判断 `chunk.version_id == document.current_version_id`。
- 影响场景：replace 后或旧向量残留时，Qdrant 仍可能返回非当前版本 chunk。
- 后果：keyword SQL 路径与 vector 路径结果不一致，混合检索可能出现过期结果。

## 5. 增量替换未停用 unchanged chunk 对应的旧版本向量点

- 文件：`backend/app/services/update_service.py:248`
- 问题：`apply_incremental_update` 为 unchanged chunk 调用 `reuse_unchanged_child_vectors` 创建新版本 Qdrant point，但只有 `diff.removed` 的旧 chunk 会被 deactivate。
- 影响场景：旧版本 unchanged child 仍保持 active，新版本也有对应 point。
- 后果：检索可同时返回旧/新两个版本的重复内容，影响排序、引用和版本一致性。

## 6. chunk diff 以 chunk_hash 作为唯一键，会丢失重复内容 chunk

- 文件：`backend/app/services/update_service.py:153`
- 问题：`calculate_chunk_diff` 用 `{chunk_hash: chunk}` 和 `{chunk_hash: record}` 构造 dict。
- 影响场景：文档包含重复模板段、相同条款、重复表格行或多个相同标题时，后一个同 hash chunk 会覆盖前一个。
- 后果：`added` / `removed` / `unchanged` 计算漏掉重复项，导致错误复用、停用或遗漏向量。

## 7. 首次创建 eval dataset item 时传入 ORM 不接受的 metadata 参数

- 文件：`backend/app/services/eval_service.py:330`
- 问题：`EvalDatasetItem` 的列映射是 `metadata_json`，但 `_get_or_create_dataset` 调用 `EvalDatasetItem(..., metadata=entry.metadata)`。
- 影响场景：数据库中尚无 dataset items 时，首次 `/api/v1/eval/run` 初始化数据集。
- 后果：触发 `metadata is an invalid keyword argument for EvalDatasetItem`，评测数据集无法初始化。

## 8. 已有 eval dataset 不会与当前 JSONL 文件重新同步

- 文件：`backend/app/services/eval_service.py:319`
- 问题：`run_eval` 每次都会读取 `dataset_path`，但 `_get_or_create_dataset` 只在 `existing_items` 为空时插入 items。
- 影响场景：修改 `eval/golden_dataset.jsonl`，或同名 `dataset_name` 指向不同 `dataset_path` 后再次运行 eval。
- 后果：后续 eval run 仍使用数据库旧 items，指标看似来自新文件但实际基于过期样本。

## 9. replace 数据库记录在 Celery 投递前已提交，投递失败会留下 queued task

- 文件：`backend/app/services/update_service.py:137`
- 问题：`process_replace` 先 commit 新 `DocumentVersion` 和 `IngestTask`，再调用 `dispatch_update_task`。
- 影响场景：Redis/Celery 不可用或 `.delay()` 抛错。
- 后果：API 返回错误，但数据库中已存在 queued replace task 和新版本，没有 worker 会处理，形成卡住状态。

## 10. replace 没有拒绝已软删除文档

- 文件：`backend/app/services/update_service.py:86`
- 问题：`process_replace` 只检查 document 是否存在和 `current_version_id` 是否存在，没有校验 `target_document.status == "active"`。
- 影响场景：对已 soft delete 的文档再次调用 replace。
- 后果：可为本应不可见的文档创建新版本和 queued task，甚至重新生成 chunk/vector，客户端也会误以为删除资源可被替换。

## 11. payload fallback 过滤忽略显式 is_active=false 请求

- 文件：`backend/app/services/metadata_filter.py:108`
- 问题：`MetadataFilter.from_input` 会保留 `filters={"is_active": false}`，但 `matches_payload_filters` 使用 `if filters.is_active and payload.get("is_active") is not True`。
- 影响场景：调用方明确请求 inactive-only。
- 后果：条件被跳过，active 与 inactive payload 都会通过过滤。

## 12. CitationChecker 不校验 quote 或 answer claim 是否真的出现在证据文本中

- 文件：`backend/app/services/citation_checker.py:62`
- 问题：引用校验主要核对 chunk/元数据身份，不验证 `citation.quote` 或答案 claim 与 `context.chunk_text` 的文本支持关系。
- 影响场景：LLM 引用一个真实 chunk_id，但编造 quote 或给出证据文本不支持的 claim。
- 后果：仍可能返回 `passed=true`，导致 citation accuracy 虚高。

## 13. query/answer 路由在 API 层直接编排业务全流程，违反薄路由分层

- 文件：`backend/app/api/query.py:116`
- 依据：`CLAUDE.md` 要求 “API routes should stay thin” 且 “flow logic should stay in services/workers”。
- 问题：route 内直接调用 `_prepare_query_pipeline`、`HybridRetriever`、`_build_evidence_contexts`、`AnswerGenerator`、`CitationChecker` 等，API 层拥有完整 query pipeline。
- 影响场景：未来增加 rerank、安全策略、日志策略、证据上下文策略时，需要同时修改 API 和 eval/服务层。
- 后果：生产路径与评测路径容易漂移，维护成本和行为不一致风险上升。

## 14. 构造 unchanged_pairs 对每个 unchanged chunk 扫描全部 persisted chunks

- 文件：`backend/app/services/update_service.py:224`
- 问题：双重列表推导对每个 unchanged 记录遍历所有 `persisted_chunks`。
- 影响场景：大文档 replace 且大部分内容未变化，例如 5000 个 child chunk 中绝大多数 unchanged。
- 后果：匹配逻辑退化为 O(n²)，replace CPU 时间显著增加。建议先按 hash/位置建立映射再匹配。

## 15. 证据上下文重建对每个 parent_chunk_id 单独 db.get

- 文件：`backend/app/api/query.py:255`
- 问题：`_build_evidence_contexts` 对 distinct parent 逐个 `db.get`。
- 影响场景：一次 `/query/answer` 返回多个不同 parent 的 child chunk，或并发查询较多。
- 后果：answer 热路径产生 N 次额外 SQL round trip，增加延迟和 DB 负载。建议批量查询 parent chunks 后用 map 回填。

## 建议修复优先级

1. **P0：replace/ingest 数据一致性**：优先修复问题 1、2、5、6、9、10，避免版本切换、索引与数据库状态错乱。
2. **P1：检索与答案正确性**：修复问题 3、4、11、12，确保 vector/keyword 结果和证据文本可信。
3. **P1：eval 可用性**：修复问题 7、8，保证 Phase 10 评测可运行且指标可信。
4. **P2：架构与性能**：修复问题 13、14、15，减少生产/评测漂移和热路径数据库/CPU 开销。
