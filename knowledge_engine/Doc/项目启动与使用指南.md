# 项目启动与使用指南

本文档基于当前仓库里的**真实代码和真实运行路径**整理，目标是让你可以从零把这个项目启动起来，并知道如何做最基本的验证。

---

## 1. 项目是什么

这是一个面向**网络安全法规、标准、教材与知识资料**的 RAG 后端项目，当前已经实现到 **Phase 10**，包含：

- 文档上传与版本化
- 文档解析、清洗、parent-child chunk
- embedding / reranker 封装
- Qdrant 向量检索 + PostgreSQL FTS
- hybrid retrieval / RRF
- safety guard / intent / rewrite / answer
- replace / 增量更新 / soft delete
- eval dataset / eval run / 指标统计

当前代码以 **FastAPI + PostgreSQL + Redis + Qdrant + Celery** 为核心。

## 2. 启动前准备

### 2.1 软件要求

建议准备：

- Python 3.11+
- Docker Desktop（如果你打算用 Docker Compose）
- PostgreSQL / Redis / Qdrant（如果你打算本地直接跑 backend）
- Windows / Linux / macOS 都可以，当前仓库命令示例以仓库里的说明为准

### 2.2 重要约束

这个仓库有一个明确约束：

> **Python 相关工作要始终使用项目专用环境，不要用用户全局 Python。**

优先推荐 conda 环境，其次是 `.venv`。

## 4. 方式一：本地 Python 环境启动

这是最适合开发调试的方式。

### 4.1 使用 conda（推荐）

在项目根目录执行：

```bash
conda create -n rag_sec_phase1 python=3.11 -y
conda activate rag_sec_phase1
pip install -e ".[test]"
```

如果你不想先激活环境，也可以直接：

```bash
conda run -n rag_sec_phase1 pip install -e ".[test]"
```

### 4.2 使用 venv（备选）

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux / macOS:
source .venv/bin/activate
pip install -e ".[test]"
```

## 5. 配置环境变量

### 5.1 基础做法

先从示例文件复制：

```bash
cp .env.example .env
```

如果你在 Windows PowerShell 里，可以手工复制或用 PowerShell 方式完成。

### 5.2 本地直跑时要注意的点

仓库里的说明指出：

- `Settings` 会从**当前工作目录**读取 `.env`
- 如果你从 `backend/` 启动 `uvicorn`，那么它会优先读取 `backend/.env`
- Docker Compose 不依赖这个问题，因为它会直接向容器注入环境变量

因此，本地直跑时建议：

- 要么把需要的 `.env` 放到 `backend/`
- 要么通过你自己的方式提前设置环境变量

## 7. 数据库迁移

当前项目在 Windows 下最稳妥的迁移方式是：**从项目根目录执行**，并显式指定 `backend/alembic.ini`。

### 7.1 推荐命令

```bash
conda run -n rag_sec_phase1 cmd /c "cd /d D:\Code_MyProject\RAG_Sec && alembic -c backend\alembic.ini upgrade head"
```

### 7.2 为什么不建议直接在 `backend/` 裸跑

当前 [alembic.ini](file:///d:/Code_MyProject/RAG_Sec/backend/alembic.ini) 的 `script_location` 是按项目根目录解析的。
如果直接在 `backend/` 下执行 `alembic upgrade head`，可能遇到：

- `Path doesn't exist: backend\alembic`

### 7.3 如果需要回退

```bash
conda run -n rag_sec_phase1 cmd /c "cd /d D:\Code_MyProject\RAG_Sec && alembic -c backend\alembic.ini downgrade base"
```

## 8. 启动 FastAPI 后端

### 8.1 本地开发方式

从项目根目录进入 `backend/`：

```bash
cd backend
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

说明：

- `app.main:app` 是 FastAPI 入口
- `--reload` 适合开发模式
- 默认端口为 `8000`

### 8.2 启动后访问地址

- API 根服务：`http://localhost:8000`
- Swagger UI：`http://localhost:8000/docs`
- 根健康检查：`http://localhost:8000/health`

## 9. 启动 Docker Compose（推荐一键体验）

如果你想最快看到完整系统编排，推荐直接使用 Docker Compose。

在项目根目录执行：




当前 `docker-compose.yml` 会拉起：

- `redis`
- `qdrant`

- 如果这些依赖没起全，根 `/health` 仍可能返回 `ok`，但 `/api/v1/health/ready` 会报告 degraded

### 10.3 查看已接入的主要接口族

当前后端可通过 OpenAPI 看到：

- `health`
- `documents`
- `query`
- `eval`

并且已做最小请求验证：

- `GET /health` → 200
- `GET /api/v1/health` → 200
- `GET /api/v1/health/ready` → 200
- `POST /api/v1/query/rewrite` → 200
- `POST /api/v1/eval/run` → 200

### 10.4 手工 API smoke 脚本

仓库提供了一个覆盖 upload / retrieve / rewrite / answer / replace / eval / delete 的手工联调脚本：

```bash
conda run --no-capture-output -n rag_sec_phase1 python backend/tests/manual_api_smoke_http.py
```

说明：脚本默认访问 `http://127.0.0.1:8000`，会自动构造两个 TXT 测试文件，并依次验证健康检查、新文档上传、检索、改写、问答、replace 增量更新、评测运行和 soft delete。此前的 PowerShell / curl 版本可作为参考，但 Windows 中文输出与 here-string 场景更容易受编码影响，日常联调优先使用 Python `urllib` 版本。

推荐先启动依赖：

```bash
docker compose up -d postgres redis qdrant
```

再启动本地 FastAPI，便于观察 uvicorn 日志：

```bash
conda run --no-capture-output -n rag_sec_phase1 python -m uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port 8000
```

同时用当前本地代码启动 Celery worker，避免 Docker 镜像未重建时 worker 仍运行旧代码：

```bash
conda run --no-capture-output -n rag_sec_phase1 python -c "import os, subprocess; os.environ['PYTHONPATH']='backend'; raise SystemExit(subprocess.call(['celery','-A','app.workers.celery_app','worker','--loglevel=info','--pool=solo']))"
```

本轮 2026-07-03 手工 smoke 结果：上述 10 个接口步骤均返回 HTTP 200。

## 11. 接口排查与测试经验

这部分是本次真实排查后沉淀下来的经验。

### 11.1 判断接口是否真的可用，不要只看 `app.routes` 的 `APIRoute`

在当前 FastAPI 0.139.0 环境中，`include_router()` 后 `app.routes` 里会出现 `_IncludedRouter`。

这意味着：

- 如果你只过滤 `APIRoute`
- 可能会误以为“业务接口没有挂载”

但实际上：

- `/openapi.json` 里可以正常出现这些路径
- `TestClient(app)` 也可以正常访问这些接口

### 11.2 推荐检查链路

建议按下面顺序检查：

1. 看 `/docs`
2. 看 `/openapi.json`
3. 用 `TestClient(app)` 或真实 HTTP 请求验证
4. 最后再把 `app.routes` 当作辅助观察，而不是唯一依据

### 11.3 本次真实检查结果

本次检查确认：

- [health.py](file:///d:/Code_MyProject/RAG_Sec/backend/app/api/health.py) 提供：
  - `/health`
  - `/health/ready`
- [upload.py](file:///d:/Code_MyProject/RAG_Sec/backend/app/api/upload.py) 提供：
  - `/documents/upload`
- [documents.py](file:///d:/Code_MyProject/RAG_Sec/backend/app/api/documents.py) 提供：
  - `/documents/{document_id}/replace`
  - `/documents/{document_id}`
- [query.py](file:///d:/Code_MyProject/RAG_Sec/backend/app/api/query.py) 提供：
  - `/query/retrieve`
  - `/query/rewrite`
  - `/query/answer`
- [eval.py](file:///d:/Code_MyProject/RAG_Sec/backend/app/api/eval.py) 提供：
  - `/eval/run`

并且 [main.py](file:///d:/Code_MyProject/RAG_Sec/backend/app/main.py) 现已显式逐个注册这些业务 router。

### 11.4 对“测试每个接口行为是否符合预期”的准确理解

当前可以确认：

- 路由已进入 OpenAPI
- 至少部分业务接口已完成最小请求验证
- 完整联调仍应继续覆盖 upload / retrieve / answer / replace / delete 的真实数据路径

也就是说，当前已经从“接口是否挂载成功”阶段，进入“逐接口业务行为验证”阶段。

## 12. 常用测试命令

仓库的 `pyproject.toml` 里配置了：

- 测试目录：`backend/tests`
- 默认只跑**非 integration 测试**
- `integration` 测试依赖真实基础设施

### 12.1 跑默认测试

```bash
conda run --no-capture-output -n rag_sec_phase1 pytest -q
```

### 12.2 跑全部 integration 测试

```bash
pytest -m integration
```

### 12.3 只跑非 integration 测试

```bash
pytest -m ""
```

### 12.4 跑单个测试文件 / 单测函数

```bash
pytest backend/tests/test_health.py
pytest backend/tests/test_health.py -k ready
```
